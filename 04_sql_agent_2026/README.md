# SQL agent

An LLM agent that answers questions about a database by writing and running its own SQL.

`sql_agent.py` creates a small SQLite database imitating an ERP finance module
(customers, invoices) and starts a prompt loop. You ask in plain language, the agent
figures out the SQL.

`sql_agent_minimal.py` is the same agent with the scenery taken away — one table, one
question, no loop — so the four lines that actually build it are visible at a glance.

| Script | What it is |
|--------|------------|
| `sql_agent.py` | Full version: two-table mock ERP, `SQLDatabaseToolkit`, prompt loop |
| `sql_agent_minimal.py` | The same agent stripped to its four essential lines |

Run both and compare the printed tool calls: the full version reaches for four tools, the
minimal one for three. Neither file says which tools to call, or in what order.

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env    # paste a free key from console.groq.com
python sql_agent.py             # full version, asks in a loop
python sql_agent_minimal.py     # one question, then exits
```

## Try

- Which customers have overdue invoices?
- What is the total overdue amount per country?
- Is any customer close to their credit limit?

## How it works

No SQL is written by hand. `SQLDatabaseToolkit` hands the model four tools:

| tool | does |
|------|------|
| `sql_db_list_tables` | lists table names |
| `sql_db_schema` | returns DDL for chosen tables |
| `sql_db_query_checker` | a second LLM pass over the draft query |
| `sql_db_query` | executes it |

The order of calls is nowhere in the code. The model derives it from the tool
descriptions: list, read schema, draft, check, run, read rows, answer. The script prints
every tool call so the loop is visible rather than magic.

## Limits

The connection is read/write. "SELECT only" sits in the system prompt, which is a
suggestion, not a control: ask the agent to delete a row and it can. Enforcement belongs
one layer down, in a read-only database user and a parser rejecting anything but a single
SELECT. Omitted here on purpose, to keep the loop readable.

The schema is four columns of clear English across two tables, so the model cannot fail.
Real ERP schemas are thousands of tables with opaque names, which is where text-to-SQL
actually breaks.

Wrong answers look like right ones. Asked which customers have no overdue invoices, the
agent once ran `status = 'Overdu'` — one letter short. The SQL was valid, it returned no
rows, and the agent reported that nobody had overdue invoices. Two of the three did.
`sql_db_query_checker` had approved the correct query a moment before: it checks the
draft, not what is finally run. Nothing failed loudly, so catching this needs a set of
questions with known answers, not a careful reading of the reply.
